# Безопасность при разработке — метод инвариантов

Адаптация методики [cloudflare/security-audit-skill](https://github.com/cloudflare/security-audit-skill) (MIT, © Cloudflare, Inc.) под слои этого скилла. Оригинал ищет дыры в готовом коде. Здесь тот же метод применяется **до** написания кода: сначала инвариант, потом слой, потом тест.

Конкретные правила с кодом — `references/security.md`, раздел «Правила по результатам аудита». Этот файл — про то, как думать, чтобы новое правило не понадобилось.

## Когда читать

Всегда, если задача задевает хоть одно:

- новый маршрут, сущность, поле с `status`/`owner`/`vendor_id`/деньгами;
- вход от чужой стороны: вебхук, callback, usage от продавца, импорт, загрузка файла;
- исходящий HTTP на адрес из данных;
- токены, пароли, почта, секреты, права;
- кэш, очередь, поиск, экспорт, отчёт — любая производная копия данных;
- удаление, отзыв, блокировка, возврат.

## Шаг 1. Инвариант — шесть строк до кода

Находка в аудите существует только при названной границе доверия. То же при разработке: нет инварианта — нечего защищать и нечего тестировать.

```
Кто:        менее доверенная сторона и что у неё уже есть (гость / покупатель с ключом / продавец / чужой сервис с секретом)
Что шлёт:   значение, действие, переход статуса или идентификатор ресурса
Контроль:   что обязано отклонить, привязать к владельцу, ограничить или отозвать
Граница:    что пересекается при провале (чужой арендатор, деньги, внутренняя сеть, права)
Ресурс:     чья запись / чей кошелёк / какой сервис пострадает
Тест:       минимальный наблюдаемый результат провала — и тест, который его ловит
```

Пример:

```
Кто:        продавец A с валидной сессией
Что шлёт:   api_id чужого API в POST /vendor/products
Контроль:   Rule::exists('apis','id')->where('vendor_id', A)
Граница:    изоляция продавцов
Ресурс:     выручка продавца B
Тест:       чужой api_id → 422, продукт не создан
```

Инвариантов на задачу обычно 2–5. Каждый превращается в тест (шаг 5).

## Шаг 2. Где живёт контроль — по файлам чеклиста

Контроль ставится на **последнем доверенном решении**, один раз. Дублирование в каждом вызове = дыра в забытом вызове.

| Файл | Вопрос безопасности, на который он обязан ответить |
|---|---|
| Migration | Уникальность включает арендатора? (`unique(['vendor_id','slug'])`, не `unique('slug')`). Частичный unique на «одна активная» (`WHERE status IN (...)`). CHECK на инварианты, которые нельзя доверить коду |
| Model | `$fillable` без `status`, `role`, `owner_id`, `commission`, `balance`. Секреты — `encrypted` + `$hidden`. Без `$guarded = []` |
| Enum | Какие переходы статуса доступны владельцу, а какие только площадке. Терминальные состояния названы |
| DTO / FormRequest | `max:` на всё. `Rule::exists()->where(владелец)`. Схема URL (`url:https`). `authorize()` не `return true` по умолчанию. `current_password` на смену почты/пароля |
| QueryBuilder | Ограничение по арендатору и жизненному циклу (`ACTIVE`, не удалён, владелец не `BLOCKED`) — один общий constraint. Пустой фильтр = пустой результат |
| Repository | Одноразовые и конкурентные операции атомарны: `UPDATE ... WHERE ... IS NULL`, `lockForUpdate`, проверка числа затронутых строк |
| Service | Переходы статусов и права владельца. Идемпотентность (ключ с владельцем). Резерв вместо check-then-act. Исходящий HTTP только через `OutboundUrlGuard`. Данные контрагента — с потолком |
| Controller / Routes | `auth` + `abilities:` + `throttle` на маршруте. Параметры маршрута недоверенные |
| Resource | Белый список полей под конкретного читателя. Ни секретов, ни внутренних цен, ни чужих идентификаторов |
| Policy | Чужое → 404. Проверяет владельца, а не только роль |
| Job / Command / Listener | У фоновой работы нет запроса: арендатор и права передаются явно и перепроверяются. `timeout`, `tries`, `backoff` |
| ServiceProvider | Boot guard: пустой/dev-секрет, тестовые адаптеры и маршруты в production |
| Tests | По тесту на каждый инвариант + печальные пути (шаг 5) |

## Шаг 3. Классы атак — пройди те, что относятся к задаче

### Изоляция арендаторов и объектов

- **Нет привязки к владельцу.** Чтение, изменение, удаление, список, счётчик или массовая операция находит объект по id и не привязывает его к владельцу — или берёт владельца из тела запроса. Проверь прямой поиск, вложенную связь, фон, админку, импорт.
- **Коллизия составного ключа.** Ключ кэша, блокировки, идемпотентности, путь в хранилище, id документа поиска не содержит арендатора. `Cache::get("report:{$id}")` — общий для всех. `"{$appId}:{$key}"` коллизирует, если части содержат разделитель.
- **Политика и запрос расходятся.** Policy проверяет одно, а запрос (`withoutGlobalScopes`, `DB::table`, агрегат, join, фоновый клиент) выбирает другое. Список отфильтрован, а счётчик или экспорт — нет.
- **Ссылка шире права.** Подписанный URL, токен скачивания, share-ссылка дают больше операций или живут дольше, чем доступ выдавшего. Привязывай операцию, точный объект, срок, арендатора.

### Производные данные

- Кэш, поисковый индекс (Meilisearch/Scout), экспорт, аналитика, логи, письма — копии. Вопрос к каждой: кто читает копию и обновится ли она при смене прав и удалении?
- Публичный ресурс и приватный ресурс одной модели — разные классы. Один `toArray()` на всех = утечка.
- Сообщение об ошибке, разница 403/404, время ответа, счётчик «найдено N» — оракул существования.

### Жизненный цикл

- **Обход удаления.** Прямой поиск, связь, поиск, фоновая задача игнорируют `deleted_at`/`revoked`/`blocked` и отдают или меняют запись.
- **Устаревшее право.** Блокировка, отзыв, смена роли или пароля не гасит токены, сессии, кэш прав, подписки, уже поставленные задачи.
- **Очередь переживает удаление.** Запись удалена, а задача в очереди, ретрай или экспорт воссоздают или продолжают использовать данные.
- **Восстановление возвращает запрещённое.** Undelete возвращает права, ключи или членство, которые нынешняя политика уже не допускает.

### Аутентификация и ключи

- Маршрут без `abilities:`; токен с `*`; выпуск мимо единого сервиса.
- Переход состояния аккаунта без повторной проверки: смена почты, пароля, привязка провайдера, отключение 2FA.
- Перечисление пользователей: разный ответ на «нет такого» и «неверный пароль»; регистрация и сброс без throttle.
- Регистр и алиасы идентификатора: `A@x.ru` и `a@x.ru`, `a+1@`, точки у gmail — один человек или два?

### Бизнес-логика и деньги

- **Гонка.** Проверка и действие разделены: баланс, лимит, остаток, «уже использовано». Пачка параллельных запросов проходит проверку вся.
- **Идемпотентность.** Повтор с тем же ключом и другим телом; ключ без владельца; ключ из заголовка клиента.
- **Границы чисел.** Ноль, отрицательное, огромное, дробное там, где ждут целое; переполнение при переводе единиц; округление в пользу плательщика.
- **Недоверенный контрагент.** Продавец сообщает usage, цену, статус доставки. Всё, что он прислал, влияет на чужие деньги — ограничь физически правдоподобным.
- **Статус, который решает не владелец.** Модерация, блокировка, KYC, выплата — владелец не должен снять их сам через «обычный» PATCH.
- **Тестовый путь.** Тестовый коннектор, фейковый адаптер, отладочный маршрут, достижимые в production.

### Вход и выход по сети

- **Исходящий запрос на адрес из данных** — SSRF (`references/security.md`, правило 1).
- **Проксирование** — путь, query, заголовки от клиента уходят дальше как есть (правило 2).
- **Входящий вебхук** — подпись, свежесть, обязательные сумма и валюта, повтор (правило 3).
- **Заголовки доверия** — `X-Forwarded-For` как источник IP без настроенных доверенных прокси.

### Исчерпание ресурсов

- **Усиление.** `per_page`, `include`, глубина JSON, регулярка, поиск `%...%`, N+1 в цикле — малый запрос даёт большую работу.
- **Накопление.** Загрузки, записи, задачи в очереди, ключи кэша без TTL растут без предела на одного пользователя.
- **Квота.** Лимит считается по ключу, который контролирует клиент, или общий на несвязанные маршруты.
- **Отказ.** Зависимость недоступна — код отказывает закрыто (fail-closed) или пропускает? Ретраи без backoff, мьютекс планировщика длиннее интервала.

## Шаг 4. Родственные пути

Один и тот же эффект почти всегда достижим несколькими путями. Контроль должен быть **равносилен** на всех, а не просто «быть»:

```
HTTP API  ·  консольная команда  ·  задача в очереди  ·  вебхук  ·  импорт/массовая операция
админка   ·  старый (legacy) маршрут  ·  ретрай и откат  ·  MCP/внутренний API
```

Нашёл корневую причину в одном месте — ищи лексические, структурные и логические варианты того же в остальных (`grep` по методу, по таблице, по ключу кэша). Сравнивай, что гарантирует один компонент и что предполагает следующий.

## Шаг 5. Печальные пути — обязательные значения в тестах

Для каждого входа, который интерфейс принимает, проверь только применимое:

```
отсутствует · пусто · ноль · отрицательное · максимум · сверх лимита · дубль
смешанная кодировка (%2e, регистр, unicode) · устаревшее · отозванное · в другом порядке
параллельно · зависимость упала · откат транзакции · чужой идентификатор · после удаления/блокировки
```

Минимальный набор теста границы: **два фиктивных арендатора через один и тот же вызов**, затем повтор после смены прав, удаления и блокировки. Реальные данные и боевые адреса в тестах не используются.

Тесты идут в дополнение к 25 кейсам из `references/testing-edge-cases.md`.

## Шаг 6. Планка находки — чтобы не шуметь

Тот же фильтр, что отсекает ложные находки в аудите, отсекает лишний код при разработке:

- Нет стороны и ресурса — это не уязвимость, а пожелание. Не усложняй код ради чеклиста.
- Не усиливай вывод: падение ≠ исполнение кода, действие над собой ≠ повышение прав.
- Факт вне исходников (nginx, `.env`, прокси, политика провайдера) не доказывает ни защиту, ни дыру. Пометь «проверить на проде» с точным вопросом — и не закладывайся на него в коде.
- Исправление — наименьшее, на последнем доверенном решении, с регрессионным тестом.

Серьёзность (для отчёта и приоритета):

| Уровень | Якорь |
|---|---|
| critical | без аутентификации: исполнение кода, полный доступ к данным, захват любого аккаунта |
| high | контроль обойдён полностью с реальным ущербом: обход аутентификации, чтение/запись чужого арендатора, деньги |
| medium | граница нарушена, но узкий радиус или редкие условия |
| low | раскрытие несекретного, эффект требует больших усилий ради малого |

Не можешь назвать конкретный ущерб — серьёзность ниже, чем кажется.

## Фаза «Аудит безопасности» — для готового кода или диффа

Триггеры: «проверь безопасность», «аудит», «security review», перед релизом денежной или публичной функции.

1. **Разведка.** `php artisan route:list` (маршрут × middleware), политики, FormRequest, задачи и команды, исходящие HTTP (`grep -rn "Http::\|curl_"`), сырые запросы (`whereRaw|DB::raw|selectRaw`), `withoutGlobalScopes`, ключи кэша.
2. **Таблица покрытия.** Строки — поверхности (маршрут, задача, вебхук), столбцы — классы из шага 3. Каждая клетка: `проверено` / `находка` / `нужна проверка на проде` / `вне объёма`. Пустая клетка ≠ «всё хорошо».
3. **Проход.** Для каждой клетки — инвариант (шаг 1), трассировка до конечной точки, родственные пути (шаг 4).
4. **Проверка.** Находку подтверждает локальный тест на фиктивных данных. Независимо перечитай сильнейший контроль, который мог её закрыть.
5. **Исправление.** Наименьшая правка + регрессионный тест; затем `pint`, `phpstan`, тесты.
6. **Отчёт.** По находке: `файл:строка`, серьёзность, ущерб, правка. Отдельно — «нужна проверка на проде» и что не покрыто.

Границы: только исходники и локальные тесты. Никаких запросов к боевым адресам, чужим сервисам и реальным учётным записям; секреты не печатаются; нагрузочных проверок доступности нет.
